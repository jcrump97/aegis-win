# AegisWin Security & Threat Model

## 1. Threat Boundaries
1. **Untrusted / Semi-Trusted MCP Agents**: External or local AI agents connected via MCP HTTP must never execute destructive or state-changing tools without human authorization, and must never access the user's PIN or raw API keys.
2. **Off-LAN LLM Providers**: Cloud LLM endpoints receive diagnostic snippets only after the user explicitly marks the calling plugin as trusted for Off-LAN transmission.
3. **LLM output**: model replies are untrusted input. They can propose a monitor rule or ask the owner a question, never act (§8).
4. **Antivirus & EDR Compatibility**: Single-binary compilation (`asInvoker`) avoids process-injection patterns and unsigned multi-binary drops.
5. **Same-user code is outside the boundary** ([ADR 0004 §3.1](adr/0004-approval-channel-and-key-hardening.md)): the approval gate protects against agents that reach AegisWin only through MCP. Code running as your Windows user can read the data folder, read AegisWin's memory while it is unlocked, replace or plant files next to the exe, and send keystrokes to its window. Run agents that can execute commands under a separate Windows account or in a sandbox if they must not be able to do these things.

## 2. Cryptographic & Storage Standards
- **Key derivation**: the PIN (6-128 characters) goes through Argon2id (64 MiB, 3 passes) with a 16-byte random salt. No PIN hash or verifier is stored; a wrong PIN shows up as an AES-GCM authentication failure. The KDF parameters and salt are bound to the ciphertext as associated data.
- **Vault encryption**: all settings, including LLM API keys and the MCP bearer token, are encrypted in `./data/vault.enc.json` with AES-256-GCM and a fresh 12-byte nonce on every save. Saves are atomic (write a temp file, flush, rename).
- **PIN Non-Exposure Invariant**: no API, MCP response, approval page or log line ever contains the PIN or the derived key.
- **One rate limit for every PIN check**: unlock, in-app approvals, gate changes, token reveal and the browser portal share a guard: 5 free attempts, then a 30-second cooldown that doubles per further failure (capped at 1 hour). PIN checks are serialized so parallel guesses cannot slip past it.

### 2.1 Rust Core Requirements ([ADR 0001](adr/0001-rust-core.md))
- **Algorithms**: Argon2id (`argon2` crate) for new vaults, AES-256-GCM (`aes-gcm`), `OsRng` for every salt, nonce, ticket ID, and CSRF token. No hand-rolled cryptography.
- **Secret memory**: the PIN, derived key, and decrypted secrets are held in `zeroize`-on-drop types inside the Rust process and wiped when the vault locks. Comparisons of verifiers and tokens use constant-time equality (`subtle`).
- **Webview boundary**: the webview is untrusted for secrets. The PIN is typed into a modal and handed to a single `invoke` for the action that needs it (`setup_vault`, `unlock_vault`, `change_pin`, a `pin_required` `run_tool`, `decide_ticket`, loosening `set_gate_policy`, `grant_llm_trust`, `reveal_mcp_token`, `enable_autostart`, `read_approval_record`, `delete_approval_record`); the UI keeps no copy in JS state and writes nothing to `localStorage`. Every PIN check goes through the global PIN guard. The webview never receives API keys or derived keys back. The MCP bearer token is the one exception: the user needs it to configure an MCP client, so it is returned only by an explicit, PIN-confirmed `reveal_mcp_token` action. API keys are write-only from the UI. Secret-bearing types do not implement `Serialize` or `Debug`, so they cannot leak into an `invoke` response or a log line by accident.
- **Webview hardening**: the UI is bundled locally (no CDN), builds the DOM with text nodes only (no `innerHTML`), and runs under a CSP of `default-src 'self'` with no `unsafe-eval`, no remote origins, `object-src 'none'`, `frame-ancestors 'none'` and `form-action 'none'`. The only Tauri capability is `core:default` on the `main` window. The WebView2 profile lives in `./data/webview`, so nothing is written to `%LOCALAPPDATA%`.
- **No demo credentials**: no build may ship a default or hardcoded PIN. A vault that doesn't exist yet means first-run PIN setup.
- **Process execution**: system binaries are launched by absolute path with argument vectors only. No shell, no `PATH` lookup, no string-built command lines (see [PLUGIN_SPEC §4](PLUGIN_SPEC.md)).

## 3. MCP Server Binding and Firewall (`aegis-core::mcp`)
- **Bind address**: `127.0.0.1` (default) or one of this PC's private IPv4 addresses (10/8, 172.16/12, 192.168/16). `0.0.0.0` and public addresses are refused, so the server is never reachable from outside the local network by configuration mistake.
- **Loopback companion**: a LAN bind also listens on `127.0.0.1` at the same port, so clients on this PC (such as the repo's `.mcp.json`) keep one fixed URL whatever the bind address. Loopback is not reachable from other machines, so this adds no exposure. If another program already holds that port on loopback, the server refuses to start (`CONFLICT`), because local clients would otherwise send their bearer token to that program. Approval links always use the bind address, so a phone on the same network can open them.
- **Lifetime**: the server runs only while the vault is unlocked. Locking stops it and forgets every ticket. Stopping closes the listeners at once, and from that moment every request on a connection that is still open gets `503` with `Connection: close`. Stop waits up to 5 seconds for those connections to finish, then returns.
- **Firewall rule**: only for a LAN bind, only when "open firewall" is on, and only when AegisWin already runs elevated: `netsh advfirewall firewall add rule name=AegisWin-MCP-<port> dir=in action=allow protocol=TCP localport=<port> localip=<bind ip> remoteip=localsubnet profile=private`. It is deleted when the server stops. A standard user gets a note instead of a UAC prompt; loopback never touches the firewall.
- **Authentication**: `POST /mcp` needs `Authorization: Bearer <token>` (24 random bytes, compared in constant time). The token can be rotated at any time, which disconnects existing clients.

## 4. Approval Tickets and the Browser Portal
- **When**: a `pin_required` tool called over MCP never runs directly. It returns `pending_approval` with a 128-bit `ticketId` and an `approvalUrl`. Tools that need administrator rights fail with `REQUIRES_ADMIN` before a ticket is opened, so the owner is never asked to approve something that cannot run. `dryRun: true` calls skip the gate because they only describe the commands.
- **Who**: the owner approves or declines in the AegisWin app or at `GET /approve/{ticketId}`. Both decisions need the PIN, so an agent cannot probe PINs or spam declines. Approval re-checks that the plugin and component are still enabled, then runs the tool in the background; the agent polls `aegis__check_ticket`. `aegis__cancel_ticket`, and the page's cancel buttons for queued requests and running plans, need no PIN (they only stop things) but the page's buttons still need the CSRF token.
- **Host and Origin validation (DNS rebinding)**: every request to `/mcp` and `/approve/*` must name the address of the listener it arrived on in `Host` (`127.0.0.1:<port>` or `localhost:<port>` on loopback, `<lan ip>:<port>` on the LAN listener; neither accepts the other's address). A present `Origin` must be the same address. `Origin: null` is refused, so the approval page sends `Referrer-Policy: same-origin` (not `no-referrer`, under which browsers send `null` on its own form post).
- **Code-written review**: a plugin can attach a description of the call, written by its code from the validated arguments (`Plugin::review_call`), such as the plain-language description and privacy warnings of a monitor rule. It is shown escaped above the raw arguments, which stay visible, and agents see the same text.
- **CSRF**: each ticket has its own 128-bit CSRF token, embedded in the approval form, compared in constant time, and never returned to agents.
- **No script, strict headers**: the portal is server-rendered HTML with every value escaped and no JavaScript. Headers: `Content-Security-Policy: default-src 'none'; style-src 'unsafe-inline'; form-action 'self'; frame-ancestors 'none'; base-uri 'none'`, `X-Frame-Options: DENY`, `Cache-Control: no-store`, `Referrer-Policy: same-origin`, `X-Content-Type-Options: nosniff`.
- **One change at a time** ([ADR 0003 §5.1](adr/0003-action-plans.md), `aegis-core::executor`): every run of a tool with `readOnly: false`, from any origin (an approved ticket, an in-app run, an `auto` call over MCP), waits for a single slot, first come first served by approval time. Read-only tools and dry runs never wait. An approved ticket shows `queued` with its own `queuePosition` and nothing about other requests. At most 10 items wait; approving an 11th fails with `CONFLICT` before the PIN is checked, so the request keeps its attempts. An item still waiting 30 minutes after approval is cancelled (`expired`). When its turn comes, the plugin, its component, and administrator rights are checked again. Lock cancels every waiting item, and none resumes after unlock (each admission carries the session it was approved in); a running change is never killed. Idle auto-lock lets the running change finish and starts nothing new meanwhile. Restart as administrator is refused while a change runs, closing the window hides to the tray instead of cutting it off, and tray Quit asks first. Two approvals of the same request arriving together cannot both run it: the ticket is checked again as it changes, and only one decision counts.
- **Action plans** ([ADR 0003](adr/0003-action-plans.md), `aegis-core::plan`): one ticket holding 1-5 fixed steps, each a tool whose manifest sets `planEligible`. When the plan is proposed, every step's arguments are validated and filled in, its plugin, component, and administrator rights are checked, and it is dry-run to collect the exact commands; any failure rejects the whole plan, and nothing runs. The supplied title and reasoning are length-limited, refused if they contain control or invisible characters, and shown under a label saying who wrote them; tools they name that are not steps are flagged. The plan is hashed (SHA-256 over canonical JSON of everything shown), and an approval must carry that hash, compared in constant time and checked before the PIN. Plans are immutable, expire after 10 minutes, and at most 5 wait at once. An approved plan holds the one change slot for all its steps, re-checks each step before it runs, and stops at the first failure (later steps `skipped`; earlier changes stay). Cancel needs no PIN, because it only does less: it withdraws a pending or waiting request, or stops a running plan before its next step. A running step is never killed. Plans the owner builds in the app (Add to plan) go through the same checks and the same PIN-and-hash approval; nothing runs when one is created.
- **Lockouts**: three wrong PINs lock the ticket (`locked_out`, HTTP 423) and the agent must ask again. Wrong PINs also count toward the global guard (HTTP 429 while it cools down). Pending tickets expire after 30 minutes.

- **Approval record** ([ADR 0003 §7](adr/0003-action-plans.md)): the engine writes every request's creation, decision (where, the owner's note, a lock-out), each system change with its outcome (from any origin, including in-app and `auto` runs), and how the request ended to its encrypted `approvals` stream. Lock records the requests it forgets. The PIN (right or wrong), CSRF tokens, and tool results are never recorded; arguments over 4 KB are recorded by size. Reading and deleting it are app-only Tauri commands that need the PIN, never MCP tools or plugin calls. Monitors see only the times and tool names of changes, to label events "during AegisWin repair".

## 5. Elevation
AegisWin always starts `asInvoker`. Tools that need administrator rights report `REQUIRES_ADMIN`, and the UI offers **Restart as administrator** (a UAC prompt via `ShellExecuteExW` with `runas`), after which the vault must be unlocked again. There is no cross-integrity job bridge: the prototype's encrypted job files were dropped (ADR 0001, Amendment 1) because one elevated process is simpler to reason about than a privileged helper that accepts requests.

## 6. Off-LAN LLM Gate and PII Sanitizer (`aegis-core::llm`)
- **LAN classification** parses the endpoint URL first. IP literals are LAN when loopback, RFC 1918, link-local, IPv6 ULA (`fc00::/7`) or IPv6 link-local; host names only when they are `localhost` or end in `.localhost`, `.local`, `.lan`, `.home`, `.internal` or `.home.arpa` (whole labels, so `fcbarcelona.com` is not LAN). Everything else is Off-LAN.
- **Relayed models count as Off-LAN.** Ollama serves its cloud models (tags `cloud` or ending in `-cloud`, e.g. `glm-4.6:cloud`, `gpt-oss:120b-cloud`) at the local endpoint but forwards every prompt to ollama.com. Such a model on a LAN host is marked `relayed`: it needs the same per-plugin trust and gets the same scrubbing as an Off-LAN host. Trust grants are cleared whenever the destination changes, meaning a new host or a switch between a local and a cloud model.
- **Trust is bound by the engine, not the plugin.** Each call gets an `LlmHandle` carrying the calling plugin's id and whether the user trusted it; a plugin cannot claim another identity. An untrusted Off-LAN call fails with `OFF_LAN_TRUST_REQUIRED` before any byte is sent.
- **Granting trust needs the PIN; revoking does not.** Trust is for a destination: changing the endpoint to a different host clears every grant.
- **Off-LAN endpoints must use `https://`.** Plain-HTTP Off-LAN URLs are refused.
- **No redirects.** The HTTP client never follows redirects, so a LAN endpoint cannot bounce a payload to an Off-LAN host.
- **Scrubbing** runs on every string in the payload before an Off-LAN call: profile paths (`C:\Users\<Name>`, also with `/`), SMB UNC server names (`\\Server\Share`), and the Windows user and computer names as whole words (case-insensitive). The PIN is never part of any payload because it is never stored.

## 7. Plugin Data and App-Only Tools (`aegis-core::plugin_data`, `registry`)
- **Plugin data lives in the vault.** A plugin's records (for example `usage-monitor`'s saved monitors) are stored inside `vault.enc.json`, so they share its encryption and atomic saves. The engine hands each plugin a `PluginStore` bound to that plugin's id, so a plugin can reach only its own records, and only while the vault is unlocked and the plugin is installed. Each plugin is capped at 256 KiB; a write over the cap changes nothing.
- **`appOnly` tools.** A tool marked `appOnly: true` is left out of MCP `tools/list`, and an MCP call to it fails with the same `unknown tool` error as a tool that does not exist, checked before anything else, so it never opens a ticket and reveals nothing. The app still reaches it through `run_tool`, with its gate applied. The in-app monitor chat uses this, because it sends the owner's own words to the LLM.

## 8. Monitors and the AI Monitor Creator ([ADR 0002](adr/0002-ai-monitor-creator.md))
- **Monitors only watch.** A rule is a closed, bounded JSON vocabulary, parsed strictly (unknown fields rejected, hidden characters rejected, process names that cannot be paths). A hit is a record; a monitor never runs anything.
- **Anyone can propose, only the owner can start.** `propose_monitor` is `auto` and saves nothing. `activate_monitor`, `pause_monitor`, `delete_monitor`, and `configure_watch_window` are `pin_required`, so an agent gets an approval request that shows the full rule and the description AegisWin generates from it.
- **Replay stays inside the watch window.** The last 30 minutes of samples are kept in memory, only inside the PIN-gated watch window and only for enabled components, so replay tells an agent no more than `capture_diagnostic_snapshot` can. A known, accepted limit: inside the window, an agent can learn whether a named process used at least 64 MB or 1 % CPU recently.
- **AI output is untrusted input.** Every chat reply must be one JSON object in an allowed form, within fixed limits, and a proposed rule must validate against the enabled components. Questions asking for secrets, containing links, code, or commands, or asking the owner to run or install something are dropped with a visible note. The AI's reasoning is shown only under an "AI-generated, may be wrong" label next to the description code generates, and a consistency check flags reasoning that names an app or event ID the rule does not watch.
- **What reaches the LLM.** The owner's description and answers, the enabled components, and, only after the owner agrees once per conversation, up to 200 running process names. Never event-log text. Every turn goes through the plugin's `LlmHandle`, so §6 (trust, `https`, scrubbing) applies, and each turn says whether it went to an on-LAN or Off-LAN LLM. The conversation is memory only and cleared on lock.
- **The app starts only what it has just described.** In the Usage Monitor tab, a proposal (from the chat or the rule editor) shows the generated description, privacy flags, and replay before its Start button, which runs `activate_monitor` behind the PIN. Editing the rule discards the check, so a rule must be described again before it can be started.

## 9. App Lifecycle: Idle Auto-Lock, Tray, and One Copy per Install ([ADR 0002 §4](adr/0002-ai-monitor-creator.md))
- **Idle auto-lock.** The vault locks after 5, 15 (default), 30, or 60 minutes without the owner; there is no "off", and other values are rejected. Only clicks or key presses in the app window and a correct PIN (app or approval page) count. Agent requests, MCP traffic, and loading the approval page never do, so an agent cannot keep the vault open. Locking stops MCP, removes the firewall rule, clears tickets, and stops every monitor except the ones that run locked (below).
- **Locked, monitoring.** A running monitor keeps going after lock, but only from what the vault declared (`run_locked` gets the vault's copy of the runtime section, never the file), and never while the runtime file waits for review. The vault key is gone; the plugin keeps nothing in memory and writes only monitor hits and heartbeats to the write-only history, which AegisWin cannot read until the PIN unlocks it. MCP, tickets, the LLM, and every tool stay off.
- **Tray.** Its menu (Open, Lock, Pause monitoring, Quit) is reachable only by someone at the desktop. It changes nothing that needs a PIN: pausing only stops recording, writes a `paused` record, and sets `paused` in the runtime file, which the tamper check ignores. Quit and a Windows shutdown are recorded as different stop reasons.
- **Close to tray** happens only while a monitor runs (also while locked) or a change runs. Otherwise closing the window quits, as before.
- **One copy per install.** A named mutex and event under `Local\`, keyed on a hash of the install folder, keep two copies from sharing one `./data`. Another program running as the same user could create these names first and stop AegisWin from starting; that user can already do far worse to `./data`, so this is accepted. If the check itself fails, AegisWin still starts.

## 10. Encrypted History on Disk ([ADR 0002 §5](adr/0002-ai-monitor-creator.md))
- **Write-only by design.** Each history stream (`usage-monitor`, `approvals`) has its own X25519 keypair. Writing needs only the public key; reading needs the private key, which is kept only inside the vault. AegisWin can therefore record while locked but cannot read back what it wrote until the PIN unlocks the vault.
- **Construction.** HPKE ([RFC 9180](https://www.rfc-editor.org/rfc/rfc9180)) base mode: DHKEM(X25519, HKDF-SHA256), HKDF-SHA256, AES-256-GCM. No other suite is compiled in or accepted. One HPKE context per segment file; each frame's additional data is the SHA-256 of the file header plus the frame index, so frames cannot be reordered, moved to another file, or replayed into another stream (the HPKE `info` names the stream and key id).
- **Crate.** `hpke` (rozbb/rust-hpke) **pinned to exactly 0.12.0**, default features off, features `alloc` and `x25519` only. It uses the same RustCrypto crates as the vault (`aes-gcm` 0.10.3, which includes the RUSTSEC-2023-0096 fix; `sha2` 0.10; `hkdf` 0.12) and `x25519-dalek` 2 on `curve25519-dalek` 4.1.3. **The crate has no paid or formal third-party audit.** Cloudflare published an internal security review of version 0.8; there is no NCC Group or comparable audit of any version. We accepted that over composing the primitives ourselves, which would be hand-rolled HPKE. To limit the risk: the pinned version runs the CFRG known-answer vector for exactly this suite in our tests, and any version bump is a reviewed change. `hpke` 0.12.0 relies on X25519 secrets being wiped on drop but does not enable `x25519-dalek`'s `zeroize` feature; `aegis-core` enables it, which turns it on for the crate's copy too.
- **Keys and handles.** Each stream's keypair is created inside the vault the first time the stream is written while unlocked. On unlock the engine caches the public keys (they are not secret) so writing continues after lock; private keys never leave the vault. Lock closes every open file, so the HPKE context held in memory while locked never covers a frame written before. A plugin reaches only its own stream (`HistoryHandle`, bound to its id); `approvals` is reserved for the engine. Purge switches the stream to a new keypair and deletes its files in one step.
- **Runtime file (`./data/runtime/<plugin>.json`).** Plaintext, written atomically: format version, stream, key id, public key, retention, the tray's `paused` flag, and the plugin's description of what it runs while locked. It reveals what is monitored, never what was recorded. The vault keeps the same content. **Tamper check:** on every unlock, before any plugin starts, each file is compared with the vault, ignoring `paused` (set from the tray without the PIN). A file that differs, cannot be read, or that AegisWin never wrote is renamed to `<plugin>.rejected.json` so it is never resumed from, and stays waiting, also across restarts, until the owner chooses to rewrite it from the vault in the app (never over MCP). Until then, changes go to the vault only. A missing file is written again from the vault. **At launch** AegisWin resumes running monitors from the file before any unlock (ADR 0002 §6), skipping a set-aside file and one with an invalid key, stream, version, or retention; the next unlock checks it and stops what the vault does not declare. Malware with write access to `./data` can therefore redirect records written while locked to its own key, add observe-only rules, or pause monitoring, until the next unlock; that is detected, not prevented (ADR 0002 §5 threat model).
- **Reading, limits, and purge need the PIN.** `usage-monitor`'s `read_monitor_history`, `configure_history_retention`, and `purge_telemetry_history` are `pin_required`, so an AI agent over MCP gets an approval request, never the history itself. The `rewrite_runtime` command behind the set-aside warning and `dismiss_resume_notice` behind the gap banner are app-only and never reachable over MCP; the banner's times come from the history, so they are shown only while unlocked. Event-log evidence shown with a gap is limited to fixed System log ids, and only User32 1074 keeps its text (who asked for the shutdown), cut to 300 characters.
- **Damage and tampering.** A frame that does not authenticate ends reading of that file. If it is the last frame (a power cut mid-write) it is dropped and the file is shown as truncated; anywhere else the file is shown as corrupt. A file written under a different key is reported, never decrypted.

## 11. Startup Shortcut ([ADR 0002 §6](adr/0002-ai-monitor-creator.md))
- **One file outside `./data/`.** Opt-in from Settings: `AegisWin Monitor.lnk` in the user's Startup folder (`FOLDERID_Startup`), written through the Shell's `IShellLinkW` COM object on a thread of its own (no shell process, no registry, no Task Scheduler). Target: this exe's absolute path; arguments `--background`; working directory the exe's folder.
- **App only, never MCP.** `get_autostart`, `enable_autostart`, and `disable_autostart` are Tauri commands, not plugin tools, so no agent can reach them. Turning it on needs the PIN (through the PIN guard) and at least one saved monitor; turning it off does not, like revoking LLM trust.
- **Another copy's shortcut is never replaced silently.** A shortcut with the same name that starts another exe (a moved folder, a new drive letter, another copy) or cannot be read is shown with *Update to this copy* (PIN) and *Remove*; enabling over it returns a conflict, and the app asks before replacing it.
- **Removal.** Turning it off deletes the file. Once the last monitor is deleted (in the app or by an approved agent request), the 5-second shell check deletes it within seconds, but only if it starts this copy. A copy whose folder was deleted cannot clean up after itself; Settings says how to remove it in Task Manager.
- **What a sign-in launch does.** `--background` opens no window and resumes only what the runtime files declare, locked (§10); it exits at once if nothing resumes. Nothing it does needs or reveals the PIN.

## 12. Known Gaps ([ADR 0004](adr/0004-approval-channel-and-key-hardening.md), accepted)
Found by the independent reviews of 2026-11-08. They are true of the current code until ADR 0004's phases land:
- **LAN mode is plain HTTP.** On the LAN address, the bearer token, every request, and any PIN typed into an approval page cross the network unencrypted. Use LAN mode only on a network you trust.
- **The approval page asks for the vault PIN, and the agent supplies its link.** A look-alike page from an agent, or anyone sniffing the LAN, can capture the PIN, and the PIN is the vault key.
- **A 6-character PIN can be guessed offline** from a copied data folder in hours.
- **The approval record is not tamper-evident.** Records can be forged by anyone with the stream's public key, and files can be deleted or cut short without detection. Writes are best effort (a failed write does not stop a change), and a flood of requests can push older records out through the size limit.
- **The plan fingerprint (8 hex characters) is a label, not proof.** An agent can make two different plans with the same fingerprint. Compare the steps, not the fingerprint.
- **The keyword checks are heuristics**: the unsafe-question filter and the reasoning-consistency notice catch common cases, not every one.
