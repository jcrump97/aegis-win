# ADR 0003: Multi-step action plans

- **Status**: Accepted (2026-11-07). Phase 1 (the serial executor) is implemented on `feat/plan-executor`, Phase 2 (`planEligible`) on `feat/plan-eligible`, and Phase 3 on `feat/plans-mcp` (the engine and MCP so far; the app's Approvals tab is next); see "As built" in §10. Phases 4-5 are not.
- **Date**: 2026-11-07
- **Related**: [ADR 0002](0002-ai-monitor-creator.md) (shared encrypted history, reasoning panels), [SECURITY_MODEL §4](../SECURITY_MODEL.md)

## Context

Every `pin_required` tool call is its own approval ticket with its own PIN entry. A common fix, such as flushing DNS, resetting Winsock, and renewing the IP address, means three tickets and three PIN entries, with no guaranteed order and no "stop if one fails".

The owner asked for a way to run several tools under one PIN. The PIN is the only thing that stops an agent from approving its own request: the browser approval page needs no other login, and the agent already holds its link. So any answer must keep "a human with the PIN approves exactly what runs".

## Options considered

1. **A 5-minute PIN grace window.** Set aside: a blanket version lets agents approve their own requests through the browser page. Even an in-app-only version covers almost no tools once the high-risk ones are excluded.
2. **Batch approve.** One PIN for several separate pending tickets.
3. **Fixed action plan.** One ticket holding an ordered list of steps with fixed arguments.
4. **Dynamic plan.** Steps may use earlier steps' outputs or branch on them.

## Decision

**Option 3.** Option 2 is dropped: plans cover its value with order, stop-on-failure, and a single reviewed list. Option 4 is rejected for v1: what runs would differ from what was approved, and tool output (for example event-log text) could steer later steps.

## 1. Plan shape

```json
{
  "title": "Reset the network stack",
  "reasoning": "DNS lookups fail after sleep; flushing the cache and resetting Winsock is the standard fix.",
  "steps": [
    { "tool": "windows-health__flush_dns", "args": {}, "reasoning": "Clears stale DNS entries." },
    { "tool": "windows-health__winsock_reset", "args": {} },
    { "tool": "windows-health__ip_release_renew", "args": {} }
  ]
}
```

- **Text limits**: `title` ≤80 characters; plan `reasoning` ≤600 characters; step `reasoning` ≤200 characters. All three are optional and AI- or agent-supplied.
- **Steps**: 1–5, no identical duplicates (the same tool with the same arguments). Each step's `args` are validated against that tool's `inputSchema`, and defaults are filled in before the plan is stored.
- **Eligible tools only.** A step must be a tool whose manifest sets `planEligible: true` (§4). Read-only and `auto` tools are not allowed; callers use them directly.
- **No `dryRun: true` steps.** A dry run is already free to call.

## 2. Review screen (in the app and on the browser page)

1. **Summary line, generated by code**, for example "3 steps · 2 need administrator · changes network settings · stops if a step fails, earlier changes stay."
2. **Each step, generated by code**:
   - step number
   - tool name and plugin
   - the manifest description
   - **every argument in full**, escaped
   - `requiresAdmin` and state-changing flags
3. **Exact commands.** When the plan is created, AegisWin runs each step with `dryRun: true` and shows the commands it would run, for example `C:\Windows\System32\ipconfig.exe /flushdns`. A plan whose dry run fails is rejected at creation.
4. **Supplied text, kept separate.** The title and reasoning appear in a panel labelled "Supplied by the requesting agent" (MCP) or "Written by you" (in-app). The same consistency check as ADR 0002 §2 flags tools the reasoning mentions that are not in the plan.
5. **Short plan hash.** The first 8 hex characters, so the owner can match what an agent said.

## 3. Binding and lifetime

- **Hash**: the stored plan (title, reasoning, and each step's tool, filled-in arguments, and reasoning) is serialized in a canonical form (sorted keys, no insignificant whitespace) and hashed with SHA-256. Everything shown on the review screen is covered.
- **Approval checks**: the approval POST carries the CSRF token **and** the plan hash. The server rejects a mismatch on either, in constant time.
- **No updates**: plans are immutable. There is no API to edit a plan or add steps; a change means a new plan and a new approval.
- **Single use, short life**: approving or declining moves the ticket to a final status once. Pending plans expire after **10 minutes** (single-tool tickets keep 30). Three wrong PINs lock the plan, as today.
- **Re-checks**: at approval and again **before each step**, the engine confirms that:
  - the plugin is still installed
  - its component is enabled
  - administrator rights are present if the step needs them

  A failed check stops the plan.
- **Pending limit**: at most 5 pending plans at once. Further proposals fail with `CONFLICT`.

## 4. Eligibility: `planEligible` in `manifest.json`

- An optional boolean, default `false`. Validation at startup rejects `planEligible: true` unless the tool:
  - is `pin_required` by default
  - is not `readOnly`
  - declares a boolean `dryRun` property
- **Initial set**: `windows-health` `flush_dns`, `sfc_scan`, `ip_release_renew`, `winsock_reset`.
- **Administrator repairs are allowed** and flagged. A plan with an admin step is refused at creation with `REQUIRES_ADMIN` unless AegisWin is already elevated, because restarting as administrator locks the vault and would discard the plan.
- **Never eligible**:
  - `purge_telemetry_history`
  - every monitor management tool from ADR 0002 (`activate_monitor`, `pause_monitor`, `delete_monitor`, `configure_watch_window`), which have their own review screen
  - the Startup shortcut, PIN, trust, gate, and token changes, which are not tools

## 5. Execution

- **Order**: after approval the ticket moves to `running` and the steps run **one at a time, in order**, on a background task.
- **Stop at the first failure.** Later steps are `skipped`. There is no "continue on error" in v1 and no rollback, since Windows repairs are not transactional. The review screen says so before approval.
- **No data flow between steps.** Each step runs with exactly the arguments that were approved.
- **Cancel** ("Stop after this step"): from the app, the browser page, or `aegis__cancel_ticket`. It needs no PIN, because it only does less. A step that is already running finishes; killing tools such as `sfc` mid-run is unsafe. `aegis__cancel_ticket` also withdraws a pending single-tool ticket.
- **Lock or auto-lock** stops the plan before its next step, and the result records `cancelled` with the reason. Auto-lock waits for the running step only (ADR 0002 §4, and §5.1 below).
- **Per-step results**: each step ends as `succeeded`, `failed`, `skipped`, or `cancelled`, with its result or error. The plan's final status is:
  - `approved`: all steps succeeded
  - `execution_failed`: includes the failed step number
  - `cancelled`: a new ticket status
  - or, as today, `declined`, `locked_out`, or `expired`

  `queued` is a new non-final status (§5.1).

  Agents poll with the existing `aegis__check_ticket`, which gains a `steps` array.
- **Lost connection**: if a step drops the network (for example `ip_release_renew`), the plan keeps running inside AegisWin and the result waits for the agent's next poll.

### 5.1 Running more than one thing at once

**Today**, every approved ticket starts at once on its own task (`Engine::decide_ticket`), and in-app runs start directly. Two approved repairs (for example `winsock_reset` and `ip_release_renew`) can run at the same time. This section replaces that.

**Decision: one global serial executor for every state-changing run.** Per-resource locks are rejected:
- they depend on every tool declaring its resources correctly, and one wrong declaration is a silent race
- several locks bring deadlock risk
- the gain is small, because repairs are rare

| Question | Decision |
| :--- | :--- |
| What is queued | Every run of a tool with `readOnly: false`, from any origin: approved plans, approved single-tool tickets, and in-app runs (PIN or `auto`). Dry runs are side-effect free and are never queued. |
| Unit of execution | A whole plan holds the executor for all its steps. Other items never interleave between a plan's steps. |
| Concurrent state-changing tools | **Never**, so there is no conflict table to maintain or get wrong |
| Read-only tools during a run | Allowed, unqueued, in parallel (snapshots, log queries, LLM analysis, `aegis__check_ticket`). Their results may reflect a system mid-change, so the app shows a "Change in progress" bar and `aegis__check_ticket` exposes the queue. |
| Order | **FIFO by approval time**: the moment a PIN decision is accepted, or an in-app Run is clicked. Not creation time, so an agent cannot reserve places by opening many tickets early. Decisions are already serialized by the PIN guard, so there are no ties. No priorities. |
| Queue size | At most 10 waiting items; a plan counts as one. Approving while the queue is full fails with `CONFLICT` *before* the PIN is checked, and the ticket stays pending. |
| Status | New status `queued` between approval and `running`, with `queuePosition`. Agents see their own item's position and "another change is running", never the details of other tickets. The app's Approvals tab lists the queue in order with a **Cancel** button on each item; the top bar shows "Running: sfc_scan (step 1/3) · 2 queued". |
| Cancel while queued | The app, the browser page, or `aegis__cancel_ticket`. No PIN, because it only does less. |
| Re-checks | **At dequeue** and before every step: plugin installed, component enabled, administrator rights present if needed. A failure ends the item as `execution_failed` with the reason. |
| Waiting too long | An item still queued 30 minutes after approval is cancelled (`expired`), because the owner approved it for the system as it was. The 10-minute pending expiry stops once a plan is approved. |
| Lock | Every queued item is cancelled with reason "locked" and **never resumes after unlock**; the approval belonged to that session. A running step finishes, since killing tools such as `sfc` mid-run is unsafe. Its outcome goes to the audit trail, and the rest of its plan is `cancelled`. Lock signals the executor and returns; it never waits on it. |
| Auto-lock | When auto-lock is due, **no new item or step starts**. The running step finishes, then the lock happens and the queue is cancelled as above. A long queue cannot hold the vault open. |
| Restart as administrator, Quit | Restart as administrator is refused while a change is running ("Wait for sfc_scan to finish"). Quit while running asks for confirmation and warns that the change may be left half done. Queued items are cancelled in both cases. |
| MCP and in-app approving the same ticket | Already safe: decisions are serialized, and the move from `pending_approval` happens once under the ticket lock. The second decision gets `CONFLICT` ("already decided"). |

**Deadlock avoidance**
- There is one executor and one slot, and nothing else to acquire.
- Tools never call other tools, and plan steps run inside the plan's slot instead of being queued again.
- The executor never holds the vault or ticket mutex across an `await`.
- Lock never waits for the executor.

**Starvation avoidance**
- Strict FIFO with no priorities, the 5-step plan cap, the 10-item queue cap, and the 30-minute queue limit.
- `os::run_system_binary` already enforces a timeout on every system binary, so no step can hold the slot forever.

**Monitor sampling during repairs** ([ADR 0002](0002-ai-monitor-creator.md))
- The sampler is read-only. It is never queued and never paused, so data keeps flowing through a repair.
- **Repairs create their own noise.** `sfc_scan` causes CPU and disk spikes, and network repairs write System events (DHCP, TCP/IP, Winsock). Monitors could fire on AegisWin's own work.
- **Annotate, don't suppress.** The engine writes `change_started` and `change_finished` records (ticket id, tool, step) to the `approvals` history stream. When history is read, monitor hits, spikes, and events inside those windows are labelled "during AegisWin repair: sfc_scan". Nothing is hidden, so a repair cannot mask a real problem.
- In *locked, monitoring* there are no tickets and the executor is idle.
- An Off-LAN LLM call or an MCP connection over the LAN can fail while a network repair runs. These are read-only and safe to retry.

## 6. MCP and in-app parity

- **One engine entry point** creates every plan, recording its origin (MCP or in-app). Both paths share validation, limits, dry runs, hashing, review, and execution.
- **MCP**: `aegis__propose_plan` returns `{ status: "pending_approval", ticketId, approvalUrl, planHash, expiresAt }`. Agents never receive the CSRF token.
- **In-app**: an **Add to plan** button next to Run on each eligible tool, then **Review and run**. The PIN is entered on the review screen. In v1 the built-in LLM does not propose plans; only MCP agents and the owner do.
- **Browser page** (`/approve/{ticketId}`): server-rendered with no script, as today. It shows the full plan, every step and argument, the dry-run commands, the labelled supplied text, and the short hash. **It always requires the PIN.** Five steps fit on one page.
- **No "approve all".** Each plan is approved on its own.
- **Single-tool tickets become one-step plans inside the engine.** Their MCP responses, 30-minute expiry, and browser page stay as they are; they skip the plan-only checks (eligibility, dry-run preview, pending-plan limit).

## 7. Audit

- **What is recorded**:
  - creation: origin, supplied title, plan hash, the steps
  - the decision: where (app or browser page), when, the owner's comment
  - every step's outcome
  - cancellations
- **Never recorded**: the PIN.
- **Today**: kept in the in-memory approvals list.
- **Persisted**: once the shared history service exists (ADR 0002 §5), to the encrypted `approvals` stream. It can be read only after unlocking, and can be purged only from the app with the PIN; there is no MCP tool for purging it.

## 8. Risks

| Risk | Mitigation |
| :--- | :--- |
| A prompt-injected agent proposes a plausible-looking plan | Steps can only be compiled-in tools that opted in. Descriptions are generated by code, dry runs show the exact commands, and supplied text is labelled. Worst case equals approving the same ≤5 repairs one by one. |
| Approval fatigue | 5-step cap on one screen, summary line, 10-minute expiry, pending-plan limit, no approve-all |
| A partly changed system after a failure | Stop at the first failure, a clear per-step report, and an up-front warning that earlier changes stay |
| Conditions change between approval and a later step | Re-checked before every step |
| Displayed text differs from what runs | The review is rendered from the stored plan, and the hash covers every displayed field |

## 10. Implementation plan

| Phase | Scope | Depends on |
| :--- | :--- | :--- |
| **1. Tickets as step lists, serial executor** | Engine models a ticket as ordered steps; single-tool tickets are one-step plans. The global serial executor (§5.1) with the `queued` status, queue caps, dequeue re-checks, and lock and auto-lock handling replaces today's concurrent runs. Restart as administrator is refused while busy. Existing MCP and portal behaviour otherwise unchanged (tests prove it). | — |
| **2. Eligibility** | `planEligible` manifest field and startup validation; mark the four repair tools | 1 |
| **3. Plans over MCP** | `aegis__propose_plan`, `aegis__cancel_ticket`, hashing, dry-run previews, limits, re-checks, sequential executor, per-step results, `cancelled` status, browser page | 2 |
| **4. In-app plans** | Add to plan, review screen with labelled text, cancel button | 3 |
| **5. Persisted audit** | `approvals` history stream | 3 and ADR 0002 Phase 4 |

**As built, Phase 1** (decided 2026-11-07, during implementation):

- **The executor** is `aegis-core::executor`: one slot, a FIFO queue of at most 10, and the 30-minute queue limit, as in §5.1. Every admission carries the session it was approved in, so an item admitted just before a lock is refused rather than surviving it. A caller that goes away (an agent disconnects) cannot cut a change off: queued work runs on its own task.
- **A ticket shows `queued` only when something is ahead of it**, so an approval with nothing else running still answers `running`, as before.
- **The step-list ticket model moves to Phase 3**, where plans first use it, so the single-tool path is reshaped once rather than twice. Phase 1 changes no ticket fields except the new `queued` status and `queuePosition`.
- **Cancel buttons** for queued items come with `aegis__cancel_ticket` in Phase 3. Until then, Lock cancels everything waiting.
- **Quit while running** asks in a Windows Yes/No box (No is the default). Closing the window while a change runs or waits hides to the tray instead.
- **The top bar** shows "Change in progress: <tool> · N waiting"; the tray tooltip names the running tool.

**As built, Phase 2**: `planEligible` also refuses `appOnly` tools, since a plan step must be reachable from both MCP and the app. Nothing reads the flag yet; Phase 3 does.

**As built, Phase 3, engine** (decided 2026-11-07, during implementation):

- **Single-tool tickets keep their own fields** rather than literally becoming one-step plans. A plan ticket adds a `plan` object (title, reasoning, origin and its label, hash, short hash, summary, consistency flags, expiry, stop reason) and a top-level `steps` array; a single-tool ticket has neither. Both go through the same decision, queue, and re-check code, so the effect is the one §9 asks for without changing what agents already parse.
- **A step that runs but reports `"success": false` has failed**, like one that returns an error. The `windows-health` repairs report a failed command that way, so without this a plan would carry on after a failed repair. Its output is kept as the step's result.
- **The plan's error names the step** ("Step 2 failed: …"); the step keeps the plain error.
- **A plan holds the one slot for all its steps**, so nothing else starts between them. Before each step it stops if it was cancelled or if idle auto-lock is waiting (`cancelled`, with the reason).
- **Lock forgets the plan** with every other ticket, as Lock does today, so an agent polling afterwards gets "ticket not found" rather than `cancelled`. The step that was running finishes; nothing after it runs. A lasting record waits for the approvals stream in Phase 5.
- **The approval must name the plan hash.** A missing or wrong hash is refused with `CONFLICT` before the PIN is checked, so a stale page costs no attempt. The single-ticket call (`decide_ticket`) passes no hash, so it cannot approve a plan.
- **A step's tool that is `appOnly` is reported to an agent as unknown**, as a direct call would be. (Phase 2 already makes such tools ineligible.)
- **Cancel** of a running single-tool request is refused with `CONFLICT`: it is one step, already running, and stopping a repair halfway is unsafe.
- **MCP** (`aegis-core::mcp`): `aegis__propose_plan` is listed only while some exposed tool is eligible, and its schema names exactly those tools. `aegis__cancel_ticket` is always listed. Any agent holding the MCP token can cancel any request it knows the id of, the same reach `aegis__check_ticket` has; cancel only does less.
- **Browser page**: the plan's form carries the full hash in a hidden `plan_hash` field. While a plan runs, the page offers "Stop after this step"; while a request is queued, "Cancel before it starts". Both are PIN-free forms that still need the CSRF token and pass the Origin check. A pending request has no cancel button on the page, so the owner is not offered two ways to say no; Decline needs the PIN, as before.
- **Found while building this: two approvals of the same request could both run it.** The decision re-read the ticket only before the PIN check, so two correct-PIN approvals arriving together (the app and the browser page at once) could both start it. The decision now re-checks that the ticket is still pending at the moment it changes it, so exactly one wins. The race predates this ADR.

## 11. Open questions

Decided on 2026-11-07 by taking the written recommendation.

1. Should a plan be allowed to mix tools from different plugins in v1? **Decided: yes**; every step is still a compiled-in, opted-in tool.
2. Should the approvals stream have its own retention setting, or share the monitor default (14 days / 64 MB)? **Decided: its own, default 90 days**, since it is small and is the audit trail.
3. Should tools that change only AegisWin's own settings (`activate_monitor`, `pause_monitor`, `configure_watch_window`) skip the queue, so they don't wait behind a 15-minute `sfc_scan`? That would need a manifest flag such as `changesWindows: false`. **Decided: queue everything in v1** (simplest, and correct if a flag is ever wrong); revisit if the wait is a real annoyance.
